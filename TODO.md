- [ ] **P2 — `delete_my_data()` erases the partner's match history, and doesn't erase what it promises.** Deleting your `members` row cascades your `swipes`, and `room_matches` requires `count(DISTINCT s.member_id) = 2` (`001_schema.sql:84`) — so the partner's matches vanish permanently, though `app/settings.tsx:101` and `lib/legal/content/privacy.ts:113` both promise they survive. In the other direction the function leaves `auth.users` (the email), `recovery_codes`, and `recovery_redeem_attempts` (raw emails, unbounded retention) intact, contradicting the policy's erasure promise. **Needs a product decision on both halves:** correct the code to match the promises, or correct the promises to match the code.
- [ ] **P2 — `redeem-recovery-code` is an account-enumeration oracle.** Unknown emails return early without recording an attempt, so only a registered email can ever reach "Too many attempts" — six unauthenticated requests confirm whether an address has an account, and the same primitive gives a renewable per-email lockout of the recovery path. One-line fix (record the failed attempt on the unknown-email branch too); needs an edge-function redeploy.
- [ ] **P2 — invite codes are brute-forceable and leak an existence oracle.** No throttle on `join_room` RPC execution (T16b tightened *sign-in*, which costs an attacker one signup total), and `room_not_found` vs `room_full` distinguishes valid codes without joining. Fix: collapse the two errors, and count attempts per caller inside the SECURITY DEFINER function. Codes also come from `random()` rather than `gen_random_bytes` — wrong primitive for a bearer credential.
