- [~] **P1 — legal-page markdown parser hangs on pipe lines. PR #33 open.** `lib/legal/parse-markdown.ts`: the paragraph branch was the only branch that could fail to advance `i`, and `isTableSep` rejected every GFM alignment row (`|:-:|`, `|:--|`, `|--:|`), so such a table header fell into it and spun forever — reproduced, the jest worker died with `FATAL ERROR ... Repo-controlled input, so not attacker-reachable, but the legal pages are statically pre-rendered and this would hang the CI export with no error — and the pending counsel edit-then-resync of the drafts is exactly the trigger. Fixed by guaranteeing forward progress + accepting standard separators, with 4 regression tests.
- [ ] **P1 — `get-restaurants` cost-abuse guard is self-authorizing; unbounded Places/Foursquare billing.** The guard restricts the requested location to `rooms.locations`, but `004_grants.sql:12` grants members UPDATE on `rooms`, so the caller writes their own allowlist. A script with one anonymous session can loop fresh random location strings (each one misses the `.eq('location', loc)` cache) and bill real money per minute, while inserting junk rows into the shared `items` table. `SessionProvider.getItems` also fans out one invoke per location with no cap on how many locations a room may hold. This re-opens the 2026-07-22 "HIGH — FIXED" item, which only ever held against callers using the UI.

  **DECIDED 2026-07-27: do both layers, provider caps first.** They cover each other's failure mode — the provider cap is the only control that bounds the actual money (including against a bug in our own logic), and the app cap is what stops one attacker from burning the shared quota and taking the restaurants deck down for real users. Provider caps alone would convert a billing attack into an availability attack; app caps alone can't bound the bill if the arithmetic is wrong.
  - **Step 1 (human, do first — `MANUAL_TODOS.md`):** daily quota limits on the Places APIs in Google Cloud + a budget alert, and the equivalent on Foursquare. Minutes, no deploy. Check current per-call pricing in the console when setting the numbers.
  - **Step 2 (code, step 3 of the ordered list above):** `CHECK (array_length(locations,1) <= 10)` on `rooms`, plus a per-user daily lookup cap of 50 enforced inside the edge function (a `places_lookups(user_id, at)` table the function writes and counts — clients can't read it). Keep the app quota comfortably under the provider quota or the app layer never fires.
  - Urgency note: exploiting this takes deliberate effort against the public anon key, and the user base is 2 people. Fix before real users arrive; not an emergency.
- [x] **P2 — `delete_my_data()` erases the partner's match history, and doesn't erase what it promises. DONE 2026-07-28 (PR #43 merged, migration 021 applied, `delete-account` deployed). Live E2E passed:** a two-member room, one side erases, the survivor still reads both matches through the snapshot, and the erased account returns `user_not_found`. Migration `021_erasure_honesty.sql` adds a `matches` snapshot table (room + item only — never the departing member's identity), makes `room_matches` read live rows UNION the snapshot so the client needs no change, rewrites `delete_my_data()` to snapshot first and then erase `recovery_codes` + `recovery_redeem_attempts`, and schedules a 30-day `pg_cron` purge of the attempts log (which closes the P3 retention item). The `auth.users` row is deleted by a new JWT-gated `delete-account` edge function that calls the RPC as the caller and then the admin API — data first, account last, so a half-failure leaves a session that can retry. Settings copy now says it ends the account; the privacy retention table states the 30 days concretely. Both manual steps are done (021 applied, `delete-account` deployed).

  **The original finding, for the record:** deleting your `members` row cascaded your `swipes`, and `room_matches` required `count(DISTINCT s.member_id) = 2` (`001_schema.sql:84`), so the partner's matches vanished permanently even though `app/settings.tsx` and `lib/legal/content/privacy.ts` both promised they survive. In the other direction the function left `auth.users` (the email), `recovery_codes`, and `recovery_redeem_attempts` intact, contradicting the policy's erasure promise.

  **DECIDED 2026-07-27 — fix the code, not the copy, on both halves.**
  - **Partner's match history: snapshot it.** Before deleting, copy the room's current `room_matches` rows into a `matches` table keyed on `room_id` + `item_id` so the record survives the swipe cascade. **The snapshot must NOT carry the departing member's identity** — room + item only — or we've retained their personal data after an erasure request and made the compliance problem worse than the bug. Rationale for choosing this over rewriting the copy: a match is a joint artifact of two people, the surviving partner has their own claim to it, and the promise is already published in `app/settings.tsx:101` and `lib/legal/content/privacy.ts:113`.
  - **Under-deletion: make it actually erase.** Add `DELETE FROM recovery_codes WHERE user_id = auth.uid()` and the matching `recovery_redeem_attempts` purge to `delete_my_data()`; deleting the `auth.users` row itself needs a small edge function (SQL can't reach the admin API cleanly). Rejected the alternative of amending the policy — publishing "when you ask us to erase your data we keep your email" is a worse position than the bug and doesn't survive a user or regulator asking why. Note this ends the account outright, which is what the button already claims.
  - **Also in this step:** a `pg_cron` purge on `recovery_redeem_attempts` (30 days) so the email log stops growing forever — this closes the P3 retention item too.
  - Standard caveat: engineering judgment about what our own published copy promises, not legal advice.
